# 일하는 방식

Whistle PRO는 혼자 만들고, 설계·계획·구현·리뷰를 Claude Code와 나눠서 한다. 모든 기능은 같은 순서를 거친다.

```
설계 문서  →  작업 계획  →  구현·테스트  →  전체 리뷰·반영  →  실기기 점검표  →  스토어 출시
(왜·목표·하지   (작업 단위,     (테스트 먼저,      (리뷰 지적을        (시뮬레이터로       (TestFlight·
 않을 것·실패    파일·이름·     작업마다 커밋)     커밋으로 남김)      못 보는 것만)       Play 내부 테스트)
 조건)          테스트 이름)
```

- **설계 문서:** 기능을 만들기 전에 대화로 "왜 필요한지, 무엇을 하지 않을지, 무엇이 실패인지"를 정하고 문서로 남긴다. 사용자가 정한 것과 설계자가 판단한 것을 구분해 적는다.
- **작업 계획:** 설계를 작업 단위로 쪼갠다. 작업마다 바꿀 파일, 함수 이름, 확인할 테스트 이름을 미리 정해 둔다.
- **구현:** 계획의 작업을 하나씩 구현하고 작업마다 커밋한다. 커밋 메시지는 `feat(watch):`, `fix(android):`, `test(ios):`처럼 범위를 붙인다.
- **리뷰:** 묶음이 끝나면 전체 변경을 리뷰하고, 지적은 "최종 검토 반영" 커밋으로 남긴다.
- **실기기 점검표:** 시뮬레이터·에뮬레이터로 확인할 수 없는 것(GPS, 진동, 화면 꺼짐, 블루투스 끊김)만 표로 만들어 실제 기기로 확인하고, 결과 칸에 날짜·기기를 적는다. 같은 동작을 고정한 자동 테스트 이름도 함께 적는다.

본체 저장소 기준 (2026-10-31): 커밋 718개(2026-10-12 ~ 10-31), 설계 문서 17개, 작업 계획 30개, 플랫폼별 실기기 점검표 3개(Apple Watch + iPhone, Android 폰, Wear OS).
